# Design

## Context

见 proposal.md。当前状态文件没有工作流档次；每个状态写操作都把不断增长的完整对象打印到对话，累计输出随步骤数快速增加。复杂澄清、OpenSpec 产物、双重审查和归档已经有独立参考文档，可按档次改变读取深度而不改变质量门禁。

## Goals / Non-Goals

**Goals:**

- 新运行默认 fast，用户用独立消息 `full` 单向升级当前运行。
- fast 不安全时可恢复地阻塞，不自动选择 full。
- 大幅减少正常状态更新和重复审查证据进入模型上下文的内容。
- 兼容升级前已经开始的运行。

**Non-Goals:**

- 不删除 OpenSpec、测试、双重代码审查或归档阶段。
- 不按文件数量、需求关键词或模型判断自动升级。
- 不新增降级命令、项目级永久默认配置或运行时依赖。

## Decisions

### 状态字段和兼容策略

`createInitialState` 写入 `workflow_profile: "fast"`。读取到没有该字段的旧状态时，仅在 `resume` 中显式迁移为 `full`；其他读取按 full 解释但不隐式改写。这样旧任务不会因插件升级降低处理深度，新任务保持用户要求的默认值。

### 显式升级和解除阻塞

新增幂等的 `state full` 操作。Skill 把用户单独输入的 `full` 映射到该操作。升级时写入 full；若当前错误是 `FULL_REQUIRED`，把被阻塞步骤改为 `interrupted`、清除错误并恢复 running，随后由正常 resume 规则核验证据。不存在任何从 full 到 fast 的操作。

### fast 阻塞边界

fast 只处理验收标准明确、没有难以逆转决策的工作。发现影响范围或验收的歧义、安全/权限/迁移规则、跨边界架构决策时，Skill 使用现有 `state block` 写 `FULL_REQUIRED`。这是一条指令级路由，不实现基于关键词的自动判定器，避免“自动升级”的变体。

### 精简状态输出

状态写命令默认输出单行 JSON 摘要：`run_id`、解析后的 profile、全局状态、当前步骤、当前步骤状态和错误代码。显式 `--json` 保持现有完整、格式化 JSON。状态文件和备份始终保存完整对象；preflight、detect 和门禁结果保持现状。

### 审查证据复用

两种档次仍按同一顺序执行原生审查和 OCR 复审。一次 OCR preview 固定共同范围，一次取得的 diff/文件内容供两轮复用；三份证据文件分别只保存本轮新增信息，汇总文件引用两轮结论而不复制测试日志。恢复后只有范围或证据失效时才重新读取。

## Risks / Trade-offs

- [用户可能不知道为何停止] → `FULL_REQUIRED` 错误必须明确提示输入 `full`，且保留当前步骤。
- [旧状态被错误当成 fast] → 缺失字段统一按 full 解释，resume 时落盘迁移。
- [摘要不足以排障] → `--json` 保留完整输出，错误摘要始终保留 code。
- [fast 被用在复杂任务] → 不自动升级，但在无法安全简化时阻塞，决定权仍属于用户。

## Migration Plan

1. 发布新版本后，新运行直接获得 fast。
2. 旧运行首次 resume 时写入 full，再按原证据恢复。
3. 回滚旧版本时新增字段会被旧代码忽略，现有状态仍可读取。
